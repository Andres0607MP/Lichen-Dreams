2. Introducción
El presente documento corresponde al entregable del Sprint 5 «Pruebas y Estabilización del Software» del proyecto Lichen Dreams. En este sprint se realizó una auditoría funcional, de integración y de estabilización del sistema, ejecutando pruebas reales sobre el código, el backend FastAPI, la base de datos MySQL, el modelo de inteligencia artificial y el frontend Flutter.
Todos los resultados aquí consignados provienen de la ejecución efectiva de pruebas durante este Sprint: la suite automatizada de pytest del backend, los tests de widget de Flutter, pruebas de API en vivo contra el servidor (HTTP), pruebas directas del modelo de IA con imágenes reales del dataset, y pruebas automatizadas web con Selenium (cuya ejecución quedó parcialmente documentada en la sección correspondiente). No se han inventado resultados exitosos: cada caso registra su resultado real y su estado.
3. Información general del proyecto

Objetivo del Sprint 5
Validar la estabilidad, el funcionamiento, la integración y el comportamiento esperado de la aplicación antes del despliegue: autenticación (registro, login, recuperación), perfil, dashboard, historial, análisis de imágenes con IA, clasificación, mapa, LiquenPedia, CRUD administrativos y validaciones; detectar y corregir los defectos encontrados y dejar evidencia real de cada prueba.

9. Entregable 4 — Reporte de Hallazgos (Bug Report)
Durante las pruebas se detectó y corrigió un defecto real de seguridad. No se documentan problemas inventados.

Comportamiento observado (antes)
Se verificó que una petición sin token a GET /imagenes devolvía 200 con 28 registros, incluidos los paths de imágenes privadas de análisis; DELETE /imagenes/31 sin token devolvía 204 (eliminaba fila y archivo).
Corrección aplicada
Se agregó autenticación obligatoria (get_current_user) a los tres endpoints, y control de propiedad/permiso (CAN_VIEW_PRIVATE_IMAGES) para imágenes privadas: el propietario conserva acceso; otros usuarios/roles sin permiso reciben 403; sin token reciben 401.
Reejecución y validación
Tras la corrección: sin token → 401 en listar/consultar/eliminar; propietario ve y elimina su imagen (200/204); otro usuario (admin sin permiso especial) recibe 403 en consultar/eliminar imágenes privadas ajenas. La suite pytest fue actualizada y ahora pasa 176/176 (ver sección 11).
- Sin token: GET /imagenes: esperado «401», obtenido «status=401» → Aprobado.
- Sin token: GET /imagenes/{id}: esperado «401», obtenido «status=401» → Aprobado.
- Sin token: DELETE /imagenes/{id}: esperado «401», obtenido «status=401» → Aprobado.
- Login propietario: esperado «200», obtenido «status=200» → Aprobado.
- Crear análisis persistido (propietario): esperado «200 + id>0», obtenido «status=200, id=32» → Aprobado.
- GET /imagenes: solo imágenes visibles (públicas + propias): esperado «contiene imagen propia», obtenido «status=200, privadas=1» → Aprobado.
- GET imagen privada propia: esperado «200», obtenido «status=200» → Aprobado.
- DELETE imagen privada propia: esperado «204», obtenido «status=204» → Aprobado.
- OTRO usuario GET imagen privada ajena: esperado «403», obtenido «sin imágenes ajenas en listado del otro usuario» → Aprobado.

10. Entregable 5 — Evidencias de Pruebas Automatizadas con Selenium
Se revisó el proyecto y no existía configuración previa de Selenium. Se implementó una infraestructura de pruebas web con Selenium 4.48 (Chrome + Selenium Manager) sobre el build Flutter Web servido en el puerto 8080. El diseño de automatización cubre: login exitoso, login con credenciales incorrectas, registro, validación de campos, consulta principal y una operación CRUD (actualización de perfil).
No obstante, la ejecución automatizada quedó interrumpida por problemas técnicos del script y del entorno (activación intermitente del árbol de semántica de Flutter Web y cierre de la sesión del navegador). Esto NO debe interpretarse como resultados de prueba: los casos no lograron completarse de forma fiable y por ello se marcan como «Bloqueados» en lo que a resultados de comportamiento respecta. Las capturas que sí se generaron evidencian que la app web se renderiza correctamente.

11. Pruebas del modelo de Inteligencia Artificial
Se validó que el modelo activo en producción es realmente el registrado como activo en la base de datos: lichen_model_v8.keras (Base de datos MySQL), sin modificar el modelo para hacer pasar la prueba.

Consideraciones sobre «desconocido» y «no es un líquen»: La aplicación NO convierte automáticamente la clase «desconocido» en «No es un líquen». El clasificador es de 3 clases (saludable/contaminado/desconocido) y, para imágenes fuera de las categorías de líquen, la predicción devuelve «liquen desconocido». No existe un rechazo explícito implementado en el modelo; se verificó que dicha lógica no existe y se documenta este comportamiento real.

17. Conclusiones
El Sprint 5 permitió validar el estado real del proyecto a través de pruebas ejecutadas y no supuestas. El backend supera sus 176 pruebas automatizadas y el frontend sus 37 pruebas; la integración frontend/backend/base de datos se confirmó mediante 38 escenarios end-to-end aprobados. El modelo de IA activo (v8) es el registrado en la base de datos y clasifica correctamente las tres categorías, documentándose el caso «desconocido» sin convertirlo en «no es un líquen».
Se detectó y corrigió un defecto de seguridad real (exposición de imágenes privadas sin autenticación), validado nuevamente por regresión. Las pruebas web automatizadas con Selenium quedaron documentadas como interrumpidas por problemas del script/navegador en el entorno, sin inventar resultados.
